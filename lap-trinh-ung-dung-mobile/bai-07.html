BÀI 07 - CSDL SQL Server nâng cao & đồng bộ dữ liệu qua backend (5 tiết: 1 LT / 4 TH)

Hai bạn cùng đặt suất cơm gà cuối cùng trong cùng một giây. Ai được phần? Và nếu hệ thống tạo đơn xong nhưng trừ tồn kho thất bại, đơn hàng đó có còn đúng không?

Mục tiêu: Hoàn thiện được thiết kế CSDL SQL Server cho nghiệp vụ thực tế (ràng buộc, chỉ mục); viết được stored procedure có giao dịch và xử lý lỗi cho nghiệp vụ nhiều bảng và báo cáo thống kê; đồng bộ được dữ liệu giữa ứng dụng và server mà không lưu CSDL trên thiết bị.

Nội dung:

  • Ý chính 1 - Toàn vẹn dữ liệu: ràng buộc CHECK, UNIQUE, khóa ngoại, giá trị mặc định; chỉ mục cho các truy vấn ứng dụng gọi nhiều.
  • Ý chính 2 - Giao dịch trong stored procedure: đặt hàng = tạo đơn + chi tiết đơn + trừ tồn kho trong một giao dịch; TRY...CATCH, ROLLBACK, THROW.
  • Ý chính 3 - Thủ tục báo cáo và script phiên bản: doanh thu theo ngày, món bán chạy; script tạo CSDL đánh số thứ tự để cả nhóm có cùng CSDL.
  • Ý chính 4 - Đồng bộ ứng dụng với server: dữ liệu chuẩn luôn ở SQL Server; optimistic update; giữ giỏ hàng khi tắt app bằng AsyncStorage.

Kết quả cần đạt: LHU Food đặt hàng an toàn khi nhiều người đặt cùng lúc; nhân viên xem được thống kê doanh thu; nhóm có ERD phiên bản cuối và script CSDL + thủ tục chạy lại được từ đầu.

CLO liên quan: CLO1, CLO2, CLO3.

📚 2. Học liệu chính ▼

2.1. Toàn vẹn dữ liệu và chỉ mục

Quy tắc dữ liệu nào đặt được ở CSDL thì đặt ở CSDL: dù request đến từ app, web hay công cụ khác, dữ liệu sai vẫn bị chặn.

-- Tồn kho không được âm
ALTER TABLE Products ADD Stock INT NOT NULL CONSTRAINT DF_Products_Stock DEFAULT 0
  CONSTRAINT CK_Products_Stock CHECK (Stock >= 0);

-- Trạng thái đơn chỉ nhận các giá trị đã thống nhất
ALTER TABLE Orders ADD CONSTRAINT CK_Orders_Status
  CHECK (Status IN (N'pending', N'preparing', N'ready', N'completed', N'cancelled'));

-- Chỉ mục cho truy vấn hay dùng: lịch sử đơn của một người, mới nhất trước
CREATE INDEX IX_Orders_UserId_CreatedAt ON Orders (UserId, CreatedAt DESC);
CREATE INDEX IX_Products_CategoryId ON Products (CategoryId) WHERE IsAvailable = 1;
  • Chỉ mục giúp SQL Server tìm nhanh mà không đọc toàn bảng. Đặt chỉ mục theo đúng điều kiện WHERE và ORDER BY mà thủ tục hay dùng.
  • Đừng tạo chỉ mục cho mọi cột: mỗi chỉ mục làm thao tác ghi chậm hơn một chút và tốn dung lượng.
  • Đặt tên ràng buộc rõ ràng (CK_..., DF_..., IX_...) để thông báo lỗi dễ hiểu và dễ sửa về sau.

2.2. Giao dịch trong stored procedure

Giao dịch (transaction) gói nhiều câu lệnh thành một khối: hoặc tất cả thành công, hoặc không có gì thay đổi. Đặt hàng gồm ba bước (tạo đơn, tạo chi tiết đơn, trừ tồn kho); nếu bước ba lỗi mà hai bước đầu vẫn được lưu, dữ liệu sẽ sai.

CREATE OR ALTER PROCEDURE sp_Order_Create
  @UserId INT, @Note NVARCHAR(200) = NULL, @ItemsJson NVARCHAR(MAX)
AS
BEGIN
  SET NOCOUNT ON;
  SET XACT_ABORT ON;                     -- lỗi bất kỳ sẽ hủy toàn bộ giao dịch
  IF ISJSON(@ItemsJson) = 0
    THROW 50400, N'Danh sách món không hợp lệ', 1;

  DECLARE @Items TABLE (ProductId INT PRIMARY KEY, Quantity INT NOT NULL);
  INSERT INTO @Items (ProductId, Quantity)
  SELECT productId, SUM(quantity)
  FROM OPENJSON(@ItemsJson) WITH (productId INT '$.productId', quantity INT '$.quantity')
  GROUP BY productId;

  IF NOT EXISTS (SELECT 1 FROM @Items) OR EXISTS (SELECT 1 FROM @Items WHERE Quantity <= 0)
    THROW 50400, N'Số lượng món không hợp lệ', 1;

  BEGIN TRY
    BEGIN TRAN;

    -- Khóa các dòng món đang đặt để hai đơn cùng lúc không cùng trừ một suất cuối
    IF EXISTS (
      SELECT 1 FROM @Items i
      LEFT JOIN Products p WITH (UPDLOCK, HOLDLOCK) ON p.ProductId = i.ProductId
      WHERE p.ProductId IS NULL OR p.IsAvailable = 0 OR p.Stock < i.Quantity)
      THROW 50409, N'Có món đã hết hoặc không đủ số lượng', 1;

    DECLARE @OrderId INT;
    INSERT INTO Orders (UserId, Note) VALUES (@UserId, @Note);
    SET @OrderId = CAST(SCOPE_IDENTITY() AS INT);

    INSERT INTO OrderItems (OrderId, ProductId, Quantity, UnitPrice)
    SELECT @OrderId, i.ProductId, i.Quantity, p.Price
    FROM @Items i JOIN Products p ON p.ProductId = i.ProductId;

    UPDATE p SET p.Stock = p.Stock - i.Quantity
    FROM Products p JOIN @Items i ON i.ProductId = p.ProductId;

    COMMIT;
    SELECT @OrderId AS orderId;
  END TRY
  BEGIN CATCH
    IF @@TRANCOUNT > 0 ROLLBACK;
    THROW;                               -- ném lại lỗi gốc (giữ mã 50409) cho backend
  END CATCH
END;
GO
  • UPDLOCK, HOLDLOCK: khóa các dòng món cho tới khi giao dịch kết thúc; đơn thứ hai phải chờ, nên không có chuyện hai người cùng lấy suất cuối.
  • THROW; không tham số trong CATCH ném lại đúng lỗi gốc; DatabaseService vẫn nhận mã 50409 và trả 409 Conflict cho app.
  • Backend chỉ gọi một thủ tục; toàn bộ giao dịch nằm trong SQL Server. Danh sách món cũng có thể truyền bằng tham số kiểu bảng (table-valued parameter) thay cho JSON.

2.3. Thủ tục báo cáo và script phiên bản

CREATE OR ALTER PROCEDURE sp_Report_RevenueByDay
  @FromDate DATE, @ToDate DATE
AS
BEGIN
  SET NOCOUNT ON;
  SELECT CAST(o.CreatedAt AS DATE)        AS day,
         COUNT(DISTINCT o.OrderId)        AS orderCount,
         SUM(oi.Quantity * oi.UnitPrice)  AS revenue
  FROM Orders o
  JOIN OrderItems oi ON oi.OrderId = o.OrderId
  WHERE o.Status <> N'cancelled'
    AND o.CreatedAt >= @FromDate AND o.CreatedAt < DATEADD(DAY, 1, @ToDate)
  GROUP BY CAST(o.CreatedAt AS DATE)
  ORDER BY day;
END;
GO

2.4. Đồng bộ ứng dụng với server

Nguyên tắc: nguồn dữ liệu chuẩn luôn là SQL Server. Ứng dụng không có CSDL riêng; ứng dụng chỉ giữ bản sao tạm để hiển thị nhanh.

Optimistic update (cập nhật lạc quan): đổi giao diện ngay khi người dùng bấm, gửi API ở nền; nếu API lỗi thì trả giao diện về như cũ.

const queryClient = useQueryClient();
const addFavorite = useMutation({
  mutationFn: (productId: number) => api(`/favorites/${productId}`, { method: 'POST' }),
  onMutate: async (productId) => {
    await queryClient.cancelQueries({ queryKey: ['favorites'] });
    const previous = queryClient.getQueryData<number[]>(['favorites']);
    queryClient.setQueryData<number[]>(['favorites'], (old = []) => [...old, productId]);
    return { previous };
  },
  onError: (_err, _id, context) => queryClient.setQueryData(['favorites'], context?.previous),
  onSettled: () => queryClient.invalidateQueries({ queryKey: ['favorites'] }),
});

Giữ giỏ hàng khi tắt app: giỏ hàng chưa đặt là dữ liệu tạm của riêng máy, lưu bằng middleware persist của Zustand với AsyncStorage (npx expo install @react-native-async-storage/async-storage):

import AsyncStorage from '@react-native-async-storage/async-storage';
import { create } from 'zustand';
import { persist, createJSONStorage } from 'zustand/middleware';

export const useCart = create<CartState>()(
  persist(
    (set, get) => ({ /* items, add, remove... như bài 04 */ }),
    { name: 'lhufood-cart', storage: createJSONStorage(() => AsyncStorage) },
  ),
);

Khi đặt hàng, server vẫn kiểm tra lại giá và tồn kho; giỏ hàng trên máy chỉ là "ý định mua", không phải dữ liệu chuẩn.

🧑‍🏫 Thực hành có hướng dẫn (2 tiết): Đặt hàng an toàn & thống kê

  2. Viết lại sp_Order_Create có giao dịch (mục 2.2). Thử: đặt số lượng lớn hơn tồn kho → nhận lỗi 50409, kiểm tra trong SSMS không có đơn nào bị tạo.
  3. Mở hai cửa sổ SSMS cùng đặt suất cuối của một món để thấy đơn thứ hai bị từ chối.
  4. Viết sp_Report_RevenueByDay, endpoint GET /reports/revenue chỉ cho staff, màn hình Thống kê trong app.
  5. Giỏ hàng dùng persist: tắt hẳn app, mở lại vẫn còn món trong giỏ.
  6. Cập nhật ERD (cột Stock, ràng buộc) và thư mục database/.

✍️ Thực hành không hướng dẫn (1,5 tiết): Món yêu thích

Thiết kế bảng Favorites (quan hệ n-n giữa người dùng và món, không cho trùng), viết các thủ tục thêm, xóa, lấy danh sách; API POST/DELETE /favorites/:productId và GET /favorites (lấy người dùng từ token); nút trái tim trong app dùng optimistic update.

Hoàn thành khi: bấm trái tim đổi màu ngay; tắt mạng rồi bấm thì giao diện tự trở lại trạng thái cũ và báo lỗi; thêm trùng một món không tạo hai dòng; mã backend không có câu SQL trực tiếp.

Nộp bài

👥 Thử thách nhóm (0,5 tiết + ở nhà)

  • Rà soát CSDL của nhóm: ràng buộc, chỉ mục, thủ tục có giao dịch cho nghiệp vụ chính, ít nhất 1 thủ tục báo cáo.

🆘 4. Góc trợ giúp và mở rộng ▼

Lỗi "Transaction count after EXECUTE indicates a mismatching number of BEGIN and COMMIT": có nhánh thoát khỏi thủ tục mà chưa COMMIT hoặc ROLLBACK. Dùng khuôn BEGIN TRY ... COMMIT ... END TRY BEGIN CATCH IF @@TRANCOUNT > 0 ROLLBACK; THROW; END CATCH như mục 2.2.

Thêm cột Stock báo lỗi vì bảng đã có dữ liệu: cột NOT NULL phải đi kèm DEFAULT như ví dụ để các dòng cũ có giá trị.

Giỏ hàng không được khôi phục: kiểm tra đã dùng cú pháp create<CartState>()(persist(...)) (có thêm cặp ngoặc) và đã cài AsyncStorage bằng npx expo install.

Kiến thức mở rộng: Tìm hiểu mức cô lập giao dịch (isolation level) và cách xem kế hoạch thực thi (execution plan) trong SSMS để đánh giá chỉ mục.

Tự đánh giá: Nếu xóa dòng WITH (UPDLOCK, HOLDLOCK), tình huống hai người cùng đặt suất cuối có thể dẫn tới kết quả gì?
