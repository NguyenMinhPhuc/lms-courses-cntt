## Bài tập hướng dẫn theo dự án LHU Food

**Nhiệm vụ:** hoàn thiện module Thông báo thời gian thực (M08) và màn hình vận hành của nhân viên (M09): khách nhận thông báo khi đơn đổi trạng thái, nhân viên thấy đơn mới ngay lập tức và chuyển trạng thái đúng trình tự. Chuẩn bị Checkpoint Sprint 3.

- **Tài liệu dùng kèm:** SRS mục 3.2.5 (actor Hệ thống thông báo), 5.9 (M08), 5.10 (F09.1, F09.2), 6.1 (sơ đồ trạng thái), mục 8 (sự kiện Socket.IO), tiêu chí US-C09, C10, S02, S03 ở mục 4.7.
- **User story:** US-C09, US-C10, US-S02, US-S03, US-SYS01, US-SYS02; mở rộng US-S06, US-C18.
- **Thời lượng gợi ý:** 2,5 tiết trên lớp.

### Chuẩn bị môi trường

```bash
cd lhu-food-api && git checkout main && git pull && git checkout -b feature/realtime
npm install @nestjs/websockets @nestjs/platform-socket.io socket.io

cd ../lhu-food && git checkout main && git pull && git checkout -b feature/realtime
npx expo install socket.io-client expo-notifications
```

Chuẩn bị **hai thiết bị** (hai điện thoại, hoặc một điện thoại và một emulator): một đăng nhập tài khoản khách, một đăng nhập tài khoản nhân viên.

### Các bước triển khai

**Bước 1. Sơ đồ tuần tự trước, mã sau.** Vẽ sơ đồ tuần tự cho hai luồng: "khách đặt đơn → nhân viên nhận `order:new`" và "nhân viên chuyển `ready` → khách nhận `order:status`" (mục 9.2.2). Đây là minh chứng CLO3.

**Bước 2. CSDL.** `database/08-notifications.sql` (mục 9.3): bảng `Notifications`, `sp_Notification_Create`, `GetList`, `CountUnread`, `MarkRead`, `sp_Order_UpdateStatus` trả `userId`.

**Bước 3. Kiểm tra đúng trình tự trạng thái (BR-15).** Bổ sung vào `sp_Order_UpdateStatus`: chỉ cho phép `pending → preparing`, `preparing → ready`, `ready → completed`; khác đi thì `THROW 50409`. Viết 3 ca thử trong SSMS (đúng, nhảy cóc `pending → ready`, đi lùi).

**Bước 4. Gateway** (mục 9.4.2): xác thực JWT trong `handleConnection`, đưa vào room `user:<id>` và `staff`; ngắt kết nối khi token sai (US-SYS01).

**Bước 5. Gửi sự kiện** (mục 9.4.3): sau `sp_Order_Create` gửi `order:new` tới `staff`; sau đổi trạng thái hoặc hủy đơn: lưu thông báo rồi gửi `order:status` (BR-14).

**Bước 6. Ứng dụng khách.** Hook `useRealtime` (mục 9.5.2), thông báo cục bộ, bấm mở `/order/<id>` (mục 9.5.3); tab Thông báo có badge (mục 9.5.4); màn hình chi tiết đơn tự cập nhật trạng thái.

**Bước 7. Màn hình nhân viên "Đơn mới"** (`app/(staff)/orders.tsx`): danh sách đơn `pending`, `preparing`, `ready` (endpoint `GET /orders/staff`, thủ tục `sp_Order_GetListForStaff` theo SRS F09.1); nhận `order:new` thì làm mới danh sách và phát thông báo cục bộ; mỗi đơn có một nút chuyển sang trạng thái kế tiếp; mở rộng: bộ lọc theo trạng thái (US-S06).

**Bước 8. Kiểm thử bốn tình huống:** ứng dụng khách đang mở, đang chạy nền, đã tắt rồi mở lại (thông báo vẫn có trong danh sách), mất mạng rồi có mạng (tự kết nối lại và làm mới).

**Bước 9. Checkpoint Sprint 3** (mục 9.8).

### Vibe coding

```text
Đọc AGENTS.md. Viết NotificationsGateway cho NestJS (Socket.IO v4) theo đặc tả F08.1 trong SRS (đính kèm):
- handleConnection: đọc token từ client.handshake.auth.token, verify bằng JwtService;
  sai thì client.disconnect(); đúng thì join room `user:${sub}`, nếu role là staff thì join 'staff'.
- Hàm notifyOrderStatus(userId, payload) emit 'order:status' tới room user; notifyNewOrder(payload) emit 'order:new' tới 'staff'.
Gateway KHÔNG ghi CSDL; việc lưu thông báo nằm ở OrdersService trước khi gọi gateway.
```

```text
Viết hook hooks/useRealtime.ts cho Expo: kết nối socket.io-client tới EXPO_PUBLIC_API_URL với auth { token }
và transports ['websocket']; kết nối lại khi token đổi; on 'order:status' thì invalidateQueries
['orders'] và ['notifications'] rồi hiện thông báo cục bộ bằng expo-notifications có data.url;
on 'connect' thì invalidate để bù sự kiện bị lỡ; cleanup thì socket.disconnect().
```

Kiểm tra kết quả AI:

- Gateway có ghi CSDL hoặc client có tự chọn room không? Cả hai đều sai nguyên tắc (mục 9.2.1).
- Phiên bản `socket.io-client` có cùng phiên bản chính với server không?
- Hook có `disconnect` khi component bị hủy hoặc token đổi? Không có thì sẽ nhận một thông báo nhiều lần.
- Thông báo có được tạo **trước** khi emit không? Tắt ứng dụng khách, đổi trạng thái, mở lại: danh sách phải có thông báo.
